# Configuration reference

Personal Execution OS reads settings from environment variables. The public
template is `.env.example`; `./scripts/start.sh` copies it to the ignored local
`.env` file and generates the required Compose secrets.

This page covers the stable settings in the public template and a few advanced
operator gates already forwarded by Compose. It does not list every inherited
tuning field in `src/app/config.py`. The presence of a typed setting does not
make it a supported public feature.

## Sources and precedence

For direct Python development, Pydantic Settings loads `.env` and then applies
process-environment values. Environment names are case-insensitive.

For Compose:

1. the root `.env` supplies Compose variable substitution;
2. `.env` is also passed to the API and worker as a backend-only `env_file`;
3. explicit values under `environment:` in `compose.yml` override matching
   values from that file;
4. the `web`, `postgres`, and `redis` containers do not receive the complete
   backend `.env`.

The API and worker both receive backend credentials because either can run an
enabled integration. This is a shared backend credential boundary, not
per-process least privilege. Protect the host, `.env`, Docker daemon, logs, and
backups accordingly.

Apply a change with:

```sh
docker compose up --build --detach --wait
```

Most settings are read when a process starts. Restart the relevant container
after editing `.env`.

## Core runtime

- `APP_ENV`: template `development`, Compose `production`; controls safe
  behavior such as hiding interactive API docs.
- `LOG_LEVEL=INFO`: accepts `DEBUG`, `INFO`, `WARNING`, or `ERROR`; logs can
  still contain sensitive operational metadata.
- `USER_TIMEZONE=UTC`: IANA timezone used for user-local schedules.
- `PRIVATE_SINGLE_USER_MODE=true`: the supported identity mode; `false` does
  not create a supported multi-user service.
- `CORS_ALLOWED_ORIGINS=http://localhost:3000` in native development and blank
  in Compose: comma-separated exact origins; the PWA is same-origin.
- `APP_PORT=8080`: loopback port published by the web service.
- `PUBLIC_HOSTNAME` (blank): one exact DNS hostname or IP for Host policy; no
  scheme, port, wildcard, path, or list.
- `VITE_SOURCE_REPOSITORY_URL` (blank): public HTTPS source link compiled into
  the welcome page; rebuilding `web` is required.

Compose publishes `127.0.0.1:APP_PORT`, even when `PUBLIC_HOSTNAME` is set. A
remote reverse proxy is a separate operator-owned boundary.

## Authentication and browser security

- `CHAT_API_KEY` (blank): optional server-to-server or legacy-development
  credential; the production browser does not store it.
- `AUTH_COOKIE_SECURE=false` locally: set `true` whenever browsers use HTTPS.
- `AUTH_TRUSTED_ORIGINS` (blank): comma-separated exact HTTPS origins for
  cookie-authenticated unsafe requests.
- `PUBLIC_HOSTNAME` (blank): Host validation only; configure browser origins
  separately.

Cookie names, session lifetime, login thresholds, and fixed bootstrap account
identifiers have typed settings but are not in the public template. Changing
them is an advanced code-level operation and needs authentication tests.
Approval controls for the dormant ad-hoc tool runtime are likewise typed
compatibility settings, not supported public configuration.

The first setup request is unauthenticated until it creates the singleton
credential. Complete setup on loopback before exposing a trusted remote
origin.

## PostgreSQL and Redis

- `DATABASE_URL` contains a native-development example; Compose replaces it
  with the `assistant_runtime` role.
- `POSTGRES_ADMIN_PASSWORD` is generated by `start.sh` for bootstrap.
- `POSTGRES_MIGRATOR_PASSWORD` is generated for the non-superuser schema owner.
- `POSTGRES_PASSWORD` is generated for the RLS-constrained API/worker role.
- `REDIS_URL` contains a native example; Compose replaces it with the internal
  queue/rate-limit/transient-state endpoint.

Do not reuse these passwords. Do not publish either service port. Redis has no
password in the supported Compose stack and relies on the internal network and
host boundary. PostgreSQL backups do not include Redis, `.env`, local identity,
or the application-data volume.

## Model and retrieval

- `LLM_PROVIDER=disabled`: accepts `disabled` or `anthropic`; the local core
  remains usable when disabled.
- `ANTHROPIC_API_KEY` (blank): required for the Anthropic provider.
- `OLLAMA_HOST` (blank): advanced query-time/dataset-curation endpoint;
  Compose commonly uses `http://host.docker.internal:11434`.
- `OLLAMA_EMBED_MODEL=nomic-embed-text:v2-moe`: model expected at that endpoint.
- `TAVILY_API_KEY` (blank): search credential; synthesis also requires a model.

Ollama is not bundled in Compose. A fresh installation does not populate
record embeddings, so setting this endpoint does not enable general semantic
record retrieval. Dataset curation uses it when that advanced job is enabled.
A remote endpoint is an external disclosure boundary.

Model names, token budgets, retrieval ratios, evaluation modes, shadow
workflows, and context limits have advanced typed settings. Their defaults are
part of the tested code. They are not public template controls because changing
them can alter cost, quality, and safety behavior.

## Google read-only connectors

- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (blank): OAuth web-client
  credentials.
- `GOOGLE_OAUTH_REDIRECT_URL` (blank): exact callback ending in
  `/api/connectors/oauth/google/callback`.
- `CONNECTOR_TOKEN_ENCRYPTION_KEY` (generated by `start.sh`): encrypts stored
  connector tokens and is required for connection and recovery.
- `GOOGLE_REFRESH_TOKEN` (blank): legacy direct-development input; the
  supported UI stores encrypted tokens instead.

The supported connector route requests read-only Calendar, Gmail, and Drive
scopes. Use **Settings > Integrations** for OAuth. The legacy
`scripts/google_oauth.py` helper is not a supported authorization path.

Losing `CONNECTOR_TOKEN_ENCRYPTION_KEY` makes stored connector tokens
unreadable. Disconnect Google before rotating it.

## Telegram

- `TELEGRAM_BOT_TOKEN` (blank): bot credential.
- `TELEGRAM_ALLOWED_USER_IDS` (blank): explicit numeric allowlist.
- `TELEGRAM_WEBHOOK_URL` (blank): externally reachable HTTPS base/exact route.
- `TELEGRAM_WEBHOOK_SECRET` (blank): secret-token header required on webhooks.

The API initializes Telegram capture/replies only when both Telegram and the
model provider are configured. The worker can initialize the Telegram bot with
the Telegram settings alone for enabled notification delivery, but individual
model-backed briefing and review jobs also require
`PROACTIVE_AUTOMATION_ENABLED=true` and an enabled model provider.

Configuring Telegram is standing authorization for the enabled worker jobs to
send their documented notification. It is not a blanket approval for dormant
ad-hoc write tools.

## Browser push

- `WEB_PUSH_PUBLIC_KEY` (blank): public VAPID key sent to the browser.
- `WEB_PUSH_PRIVATE_KEY` (blank): private VAPID signing key.
- `WEB_PUSH_SUBJECT=mailto:owner@example.com`: operator contact URI required by
  the protocol.

Push subscription records are stored locally. Delivery uses a browser-vendor
push service and is therefore an external metadata boundary.

## Operator automation

Each control below has its own gate. Some also depend on a model, Ollama,
Telegram, or another master gate. Enable them one at a time. Controls labelled
**advanced** do not appear in `.env.example`; adding one manually requires
source review and operator testing.

Every gate defaults to `false`:

- `PROACTIVE_AUTOMATION_ENABLED` adds model schedules when a model is enabled.
- `SESSION_MAINTENANCE_ENABLED` compacts/removes evidence under the retention
  contract below.
- `AUTO_JUDGE_ENABLED` permits additional model evaluation.
- `DATASET_CURATION_ENABLED` writes proposals for later human promotion.
- `EVAL_PIPELINE_ENABLED` runs periodic evaluation summaries.
- `EVAL_EXPORT_ENABLED` writes evaluation exports to `app-data`.
- `SPOTCHECK_ENABLED` creates a human-review queue and Telegram nudge.
- `COST_ALERTS_ENABLED`, `QUALITY_ALERTS_ENABLED`, and `SLO_ALERTS_ENABLED`
  evaluate their respective thresholds and can deliver alerts.
- `QUALITY_GATES_ALERTS_ENABLED`, `SCHEMA_DRIFT_ALERTS_ENABLED`, and
  `DLQ_ALERT_ENABLED` are advanced gates for quality/security, schema, and aged
  dead-letter alerts. Schema-drift alerts also require
  `SCHEMA_DRIFT_ALERT_LOG_PATH` to name an operator-managed JSON-lines
  structlog file; the default Docker logging driver does not create one.
- `GITHUB_ISSUE_FILER_ENABLED` creates and maintains issues in the configured
  repository.

Some jobs are present in the cron schedule even when disabled; their worker
function exits without performing the protected behavior. Model cron jobs are
omitted entirely unless both the model and proactive automation are enabled.

Enabling an alert or issue filer gives that job standing permission to perform
its documented external action. Review the destination, token scope,
deduplication, cost, and disable path first.

### Schedule and dependency contract

User-local schedules are converted to UTC when the worker starts. The current
implementation uses the UTC offset at that moment; a worker left running across
a daylight-saving transition can drift by one hour until it restarts. Restart
the worker after a timezone or DST-offset change.

The always-registered group contains:

- heartbeat at minutes 0 and 30;
- cost alerts hourly at minute 25 and dead-letter alerts hourly at minute 50;
- quality, SLO, quality-gate, and schema-drift checks daily at 09:00, 09:15,
  09:30, and 09:45 user-local time;
- session maintenance at 02:30, evaluation export at 03:00, evaluation
  pipeline at 03:05, and idempotency cleanup at 03:45 user-local time;
- dataset proposal curation on Monday at 04:00, GitHub issue sync daily at
  06:15, and the spot-check nudge on Friday at 14:00 user-local time.

Registration does not mean activity: each protected function checks its own
gate and dependencies. In particular, dataset curation requires
`DATASET_CURATION_ENABLED=true` **and** a working `OLLAMA_HOST`; it does not
use the dormant RSS curation task.

The model schedule exists only when Anthropic and
`PROACTIVE_AUTOMATION_ENABLED=true` are both configured. It checks scheduled
actions every minute, runs the briefing at 08:00, pattern detection at 20:00,
the weekly review Sunday at 19:00, monthly/quarterly/annual reviews on their
respective first day at 10:00, and consolidation at 03:30 user-local time.
Auto-judge is in this group, runs at minute 15 of UTC hours 00, 04, 08, 12, 16,
and 20 by default, and still no-ops unless `AUTO_JUDGE_ENABLED=true`.

### Session-maintenance retention contract

`SESSION_MAINTENANCE_ENABLED=true` authorizes destructive changes to
PostgreSQL runtime evidence at 02:30 user-local time:

- interaction request and response text older than 90 days is replaced by a
  marker plus a 240-character preview;
- artifact payloads older than 30 days and at least 8,000 serialized characters
  are replaced by a compact type-specific summary;
- resolved workflow checkpoints older than 30 days are deleted; pending
  checkpoints are retained.

The job changes PostgreSQL only; it does not clean browser data, provider data,
backups, or files in `app-data`. There is no dry-run mode. Before enabling it,
create and verify a database backup, run the maintenance unit tests, and test a
restore with disposable data. To stop future runs, set the gate to `false` and
restart the worker. To recover already compacted or deleted content, restore a
backup from before the run; disabling the gate cannot reconstruct it.

The retention periods, preview length, and size threshold are advanced typed
settings and do not appear in `.env.example`. Changing them requires a
source-level review and retention tests.

## GitHub issue filing

- `GITHUB_TOKEN` (blank): dedicated token scoped to one repository.
- `GITHUB_ISSUE_FILER_ENABLED=false`: master gate.
- `GITHUB_ISSUE_REPO` (blank): exact `owner/repository` destination.

The worker can create and maintain issues without per-event confirmation once
enabled. This path is for operator quality signals, not general user-directed
GitHub automation.

## Observability and heartbeat

- `SENTRY_DSN` (blank) enables external errors;
  `SENTRY_SEND_DEFAULT_PII=false` must remain false unless disclosure expands.
- `POSTHOG_API_KEY` and `POSTHOG_HOST` (both blank) must both be set to enable
  product events.
- `OTEL_ENABLED=false` plus a blank `OTEL_EXPORTER_OTLP_ENDPOINT` keeps trace
  export off; `OTEL_EXPORTER_OTLP_HEADERS` contains sensitive collector
  headers.
- `OTEL_EXPORT_CONTENT=false` is an advanced separate content-export control.
- `HEALTHCHECKS_HEARTBEAT_URL` (blank) receives the worker heartbeat when set.

`HEALTHCHECKS_BACKUP_URL` exists as an inherited typed field but is not used by
the supported backup scripts. Do not configure it expecting backup monitoring.

Read [Observability](OBSERVABILITY.md) before sending telemetry off-host.

## Privacy controls

- `PII_REDACTION_ENABLED=true` applies the implemented defence-in-depth
  redaction layer to supported log/provider paths.
- `SENTRY_SEND_DEFAULT_PII=false` prevents default PII capture.
- `OTEL_EXPORT_CONTENT=false` prevents deliberate span-content export.

Redaction is not authorization to log or transmit personal data. New fields and
provider calls still require a data-flow review.

## Outbound URL and RSS fetching

A user-directed save flow can fetch a supplied HTTP(S) URL through
`src/app/core/url_extractor.py`. The fetcher validates destinations, blocks
unsafe address classes, bounds redirects, time, and response size, and treats
retrieved content as untrusted. The remote site still sees a request from the
host and can return hostile content.

The content-curation worker contains raw RSS polling code, but this release has
no supported feed-configuration UI, schedule, enqueue path, or public gate. It
is dormant and does not inherit the supplied-URL fetcher's SSRF controls.
Do not expose it as an operator feature without a separate URL-security review,
feature gate, schedule, failure policy, and documentation.

## Safe change checklist

Before adding a setting:

1. Give it a safe default.
2. Validate incompatible combinations at startup.
3. Decide whether it is public, advanced, inherited, or unsupported.
4. Add it to `.env.example` only when the operator path is supported.
5. Add it to the appropriate service in `compose.yml`. Do not assume
   `env_file` belongs on a frontend or data container.
6. Test the default, enabled, invalid, and missing-secret cases.
7. Update integration, privacy, security, cost, retention, and recovery
   documentation as applicable.
